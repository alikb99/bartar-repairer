# صفحات frozen (HTML آماده در public/)

این پنج مسیر به‌صورت HTML از پیش رندرشده اینجا نگهداری می‌شوند، نه به‌عنوان route:

| مسیر | چیست |
|---|---|
| `/acer/` | لندینگ دست‌ساز برند ایسر، با پوشه‌ی `assets/` مستقل خودش. هیچ‌وقت خروجی Next نبوده. |
| `/prices/` | جدول قیمت تعمیر ۲۴۷ مدل |
| `/mobile-repair-online/` | لندینگ تعمیر آنلاین با پیک |
| `/app/` | لندینگ دانلود اپلیکیشن اندروید. دست‌ساز و مستقل (CSS درون‌خطی، `img/` و `fonts/` خودش، APK نسخه‌ی ۱٫۵٫۰). `bartar-app.apk` قدیمی هم برای حفظ URL نگه داشته شده. |
| `/warranty/` | استعلام کد گارانتی. دست‌ساز و مستقل، فرمش embed سایت 9fx است. |

`/app/` و `/warranty/` در ۷ مهر ۱۴۰۵ از نسخه‌ی زنده‌ی سایت (پوشه‌ی `new/`) به اینجا آورده شدند؛ قبل از آن فقط روی هاست وجود داشتند و هر دیپلوی از روی این ریپو آن‌ها را پاک یا به نسخه‌ی قدیمی برمی‌گرداند. برای نسخه‌ی جدید اپ: APK جدید را در `public/app/` بگذار و لینک‌های `index.html` را عوض کن.

## چرا

سه موردِ آخر در بازه‌ی ۲۵ جولای تا ۱۶ آگوست ۲۰۲۶ به‌عنوان صفحه‌ی React ساخته شدند، ولی سورسشان هرگز کامیت نشد و روی هیچ ماشینی باقی نمانده (جزئیات در `docs/00-CRITICAL-source-location.md` داخل پوشه‌ی دیپلوی). آنچه باقی مانده فقط HTML نهایی روی سایت زنده است.

کپی‌کردن همان HTML به اینجا آن‌ها را **بایت‌به‌بایت** بازتولید می‌کند و ریسک سئو صفر است — در حالی که بازنویسی‌شان از روی HTML قطعاً باعث تغییر متن یا چیدمان می‌شد.

## هزینه‌اش

این صفحات از layout مشترک جدا هستند. یعنی هر تغییر سراسری در هدر/فوتر/اسکیما **روی آن‌ها اعمال نمی‌شود** و باید دستی در همین فایل‌های HTML هم اعمال شود. قبل از هر تغییر سراسری، این چهار فایل را هم چک کن.

ورودی‌های sitemap آن‌ها دستی در `app/sitemap.ts` تعریف شده‌اند، چون `POSTS` از وجودشان خبر ندارد.

## راه درست در آینده

هرکدام را که به‌عنوان route واقعی Next بازنویسی کردی، پوشه‌اش را از `public/` حذف کن و ورودی دستی‌اش را از `app/sitemap.ts` بردار. `/prices/` بهترین گزینه برای شروع است، چون داده‌اش (`content/parts-prices.json`) همین حالا در ریپو هست.

## هشدار: هرگز دو بیلد را هم‌زمان اجرا نکن

`prebuild` در شروع هر بیلد کل `out/` را پاک می‌کند. اگر دو بیلد هم‌زمان اجرا شوند، خروجی همدیگر را می‌شویند و یک `out/` ناقص باقی می‌ماند (در عمل ۷۶۰، ۶۷۸ و حتی ۷ صفحه دیده شد) بدون اینکه خطایی بدهد.

بدتر: هر اسکریپت مقایسه‌ای که در آن لحظه اجرا شود، همان پوشه‌ی ناقص را می‌خواند و نتیجه‌ی «همه‌چیز درست است» می‌دهد.

قبل از هر بیلد `Get-Process node` را چک کن و منتظر بمان تا بیلد قبلی کامل تمام شود؛ بعد مقایسه بگیر.

## این صفحات دیگر JS ندارند — و نباید داشته باشند

۱۲ شهریور ۱۴۰۵ این سه صفحه روی سایت زنده بی‌استایل بودند و بعد یک ثانیه سفید می‌شدند. دو علت پشت سر هم:

۱. **CSS کهنه.** به `css/1919a130d237539c.css` اشاره می‌کردند که دیگر تولید نمی‌شد (۴۰۴). هش CSS به کل مارک‌آپ سایت وابسته است و با هر بیلد عوض می‌شود، پس این خود‌به‌خود کهنه می‌شود.

۲. **هیدریشن شکست‌خورده.** هر فایل ۱۰ تگ `<script>` و ~۴۵ بلوک `self.__next_f.push` (پی‌لود RSC) داشت که به module graph یک بیلد قدیمی اشاره می‌کردند، از جمله `app/prices/page-*.js` که سورسش گم شده و هرگز برنمی‌گردد. تا وقتی آن چانک‌ها هم ۴۰۴ بودند React اصلاً بوت نمی‌شد و صفحه فقط بی‌استایل می‌ماند؛ به‌محض اینکه هش چانک‌های مشترک درست شد، React بوت شد، ماژول گمشده را پیدا نکرد و کل DOM را پاک کرد.

راه‌حل: **تمام JS مربوط به Next از این سه فایل حذف شد** — تگ‌های `<script src="/_next/...">`، preloadهایشان، و کل پی‌لود RSC. هر سه اسکیمای JSON-LD، متن، و ۳۱۱ ردیف جدول قیمت دست‌نخورده ماندند (حجم فایل‌ها ~۶۰٪ کم شد). این صفحات حالا HTML خالص‌اند و هرگز نمی‌توانند هیدریت شوند.

**هزینه‌اش:** تعاملات سمت کلاینت از بین رفت — جستجوی مدل و فیلتر برندها در `/prices/`، و منوی موبایل. این‌ها از قبل هم کار نمی‌کردند (چانک صفحه ۴۰۴ بود)، پس چیزی از دست نرفت. اما یعنی راه درست همچنان بازنویسی `/prices/` به‌عنوان route واقعی است.

**قواعدی که از این به بعد باید رعایت شوند:**

- هرگز به این سه مسیر با `<Link>` لینک نده — فقط `<a>` ساده. `<Link>` ناوبری سمت کلاینت می‌کند و چون این صفحات runtime ندارند، نتیجه صفحه‌ی سفید است. (فوتر و `PagePriceTable` به همین دلیل `<a>` هستند.)
- فایل‌های `index.txt` (پی‌لود RSC برای ناوبری کلاینت) حذف شدند و نباید برگردند؛ نبودشان باعث می‌شود روتر به full page load برگردد.
- هش CSS دیگر دستی نگه‌داری نمی‌شود: `scripts/fix-frozen-css.mjs` در `postbuild` اجرا می‌شود، هش واقعی هر بیلد را از `out/index.html` می‌خواند و در هر سه صفحه‌ی خروجی جایگذاری می‌کند. اگر صفحه‌ای گم یا بدون `<link>` باشد، بیلد را می‌شکند.
- کلاس‌های Tailwind این صفحات فقط وقتی تولید می‌شوند که هر سه فایل در `content` داخل `tailwind.config.ts` باشند. اگر از آنجا حذف شوند، صفحه نیمه‌استایل می‌شود.

## هشدار: بیلد را در Git Bash با pipe اجرا نکن

- `npm run build | tail -n` باعث SIGPIPE و کشته‌شدن بیلد وسط کار می‌شود.
- `npm run build` در Git Bash با `exit 127` شکست می‌خورد (`next` در PATH آن شل نیست) — ولی `prebuild` موفق اجرا می‌شود، پس خروجی گمراه‌کننده است.

بیلد را در PowerShell اجرا کن و خروجی را به فایل بفرست (`*> build.log`)، نه به pipe.
